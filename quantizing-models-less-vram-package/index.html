Quantizing Models to Fit in Less VRAM

How lower-precision weights make bigger models practical on smaller GPUs and laptops.

Quantization is the main reason large language models can run on modest hardware.

By storing model weights in fewer bits, you dramatically reduce memory usage and often make a model usable on a smaller GPU, consumer laptop, or edge device. The trade is that lower precision can slightly reduce quality, change speed characteristics, and limit what kinds of training you can do.

Executive summary

  • Weights consume most of the baseline VRAM footprint.
  • Fewer bits per weight means fewer bytes in memory.
  • 4-bit and 5-bit quantization often unlock local inference for models that would not otherwise fit.
  • Quantization is usually safer for inference than for full training.
  • Sometimes the better answer is not quantization, but a smaller model with stronger overall quality.

What Quantization Is

Core idea

Quantization means representing model values with fewer bits than the original training format. Instead of storing each weight as FP16, BF16, or FP32, the runtime stores weights in INT8, 6-bit, 5-bit, 4-bit, or another compressed representation.

The model still performs similar math at inference time, but the stored parameters are compressed and then dequantized or used in specialized kernels during computation.

What usually gets quantized

  • Weights: the most common target because they dominate memory footprint.
  • Activations: sometimes quantized for additional savings, but this is harder and can affect quality more.
  • Optimizer states: relevant in training, not just inference.
  • KV cache: sometimes compressed during long-context inference to save additional VRAM.
Important: quantization does not magically make a model smarter. It is a compression and deployment strategy, not a capability upgrade.

Why Quantization Reduces VRAM Usage

FP16 / BF16

16 bits

About 2 bytes per weight.

INT8

8 bits

About half the weight memory of FP16.

4-bit

4 bits

Roughly one quarter of FP16 weight storage before metadata overhead.

Mental model

If a model has billions of parameters, every saved bit matters. A 7B model stored in FP16 needs roughly 14 GB just for the raw weights. Store those same weights in 8-bit and the weight memory drops to around 7 GB. In 4-bit, the raw weight storage drops to roughly 3.5 GB, plus extra overhead for scales, group metadata, temporary buffers, and runtime implementation details.

Real VRAM usage is always higher than raw weights alone because inference also needs activations, attention workspace, the KV cache, framework overhead, and sometimes extra staging buffers. Even so, quantizing weights is often the biggest lever.

Why the savings are not perfectly linear

  • Quantized formats often store per-group or per-channel scale values.
  • Some layers stay in higher precision for stability.
  • The runtime may dequantize chunks into temporary compute buffers.
  • KV cache growth can dominate memory at long context lengths.

What quantization helps most

  • Fitting a model on a smaller GPU
  • Increasing room for context length or batch size
  • Running local inference on laptops and desktops
  • Reducing memory bandwidth pressure in some runtimes

FP16

Half precision floating point. Good default for inference when memory is available. A common reference point when comparing quantized variants.

BF16

Bfloat16 uses 16 bits too, so it does not save VRAM versus FP16, but it often behaves better during training due to wider dynamic range.

INT8

Popular because it cuts memory in half while often preserving most model quality for inference tasks.

6-bit

Less universal than 8-bit or 4-bit, but attractive when you want extra compression without going all the way down to the most aggressive low-bit modes.

5-bit

Frequently seen in local-LLM communities because it can preserve noticeably more quality than some 4-bit variants while still fitting in tight VRAM budgets.

Quality and Speed Tradeoffs

Quality tradeoffs

  • Lower-bit formats can slightly reduce factual recall, reasoning reliability, or output consistency.
  • Sensitive layers may lose precision in ways that show up on math, coding, or multilingual tasks.
  • Smaller models suffer more from aggressive quantization than very overprovisioned models in some workloads.
  • The lower the bit width, the more important the quantization algorithm becomes.

Speed tradeoffs

  • Quantization can improve speed when memory bandwidth is the bottleneck.
  • It can also slow things down if kernels are poorly optimized or if repeated dequantization is expensive.
  • CPU, CUDA, Metal, and ROCm all have different sweet spots.
  • A quantized model that fits entirely in VRAM may beat a higher-precision model that spills or cannot run at all.

Reality check on performance

People sometimes assume lower bits always mean faster generation. That is not guaranteed. If your runtime has excellent kernels for a given quantization format, speed may improve. If not, a higher-precision format can actually be faster. Always benchmark tokens per second, prompt processing speed, and memory usage on your actual machine.

How Quantization Affects Inference vs Fine-Tuning

Inference

Quantization is most mature and most commonly used for inference. You take a trained model, convert or download a quantized version, and run it with a runtime that supports the chosen format. This is the standard local deployment pattern.

  • Usually the easiest win
  • Big memory reduction
  • Often acceptable quality loss
  • Ideal for local serving and experimentation

Fine-tuning

Full training directly in very low precision is harder. Training is more sensitive than inference because gradients, optimizer states, and activations all matter. That is why many workflows use parameter-efficient tuning instead of full low-bit training.

  • QLoRA keeps the base model quantized, then trains LoRA adapters
  • This dramatically reduces VRAM needs for adaptation
  • You still need enough memory for activations and optimizer-related state
  • Not every training recipe or model architecture behaves equally well

Why QLoRA matters

QLoRA is one of the most important practical developments for small-budget fine-tuning. The base model is stored in 4-bit form, while trainable adapters are learned on top. This makes it feasible to adapt models that would otherwise require much larger GPUs.

Limits of low-bit training

If your goal is maximum training quality on a demanding task, a heavily quantized base may impose a ceiling. Quantized fine-tuning is excellent for many practical adaptations, but it is not always equivalent to full higher-precision training.

Common Tools and Runtimes

llama.cpp / GGUF

Widely used for local inference on CPU, CUDA, and Apple Silicon. Popular for 4-bit, 5-bit, and 6-bit model files intended for offline use.

Ollama

User-friendly local serving layer built on common open model runtimes. Good for trying quantized models quickly with minimal setup.

Transformers + bitsandbytes

Common Python path for 8-bit and 4-bit loading in research and application code. Frequently used in QLoRA-style workflows.

ExLlama / ExLlamaV2

Optimized inference engines for certain quantized LLM formats on NVIDIA GPUs, often chosen for high-throughput local generation.

vLLM and TensorRT-LLM

Important serving stacks for production inference. Quantization support varies by version and hardware target, so verify exact compatibility.

AutoGPTQ / AWQ / GPTQ-style tools

Families of post-training quantization approaches used to produce efficient deployment artifacts with different quality and speed properties.

Tool selection rule: choose the runtime first based on your hardware and deployment target, then choose the model format that runtime handles best.

A Practical Quantization Workflow

1

Start with the model in its original recommended inference format, usually FP16 or BF16, and measure quality plus VRAM usage.

2

Define the real constraint: GPU VRAM, laptop RAM, target tokens per second, context length, or serving cost.

3

Try a conservative option first, such as INT8 or a higher-quality 5-bit quant, before jumping to the smallest possible file.

4

Benchmark memory footprint, prompt ingestion speed, decode speed, and task quality on a representative prompt set.

5

If the model still does not fit, move to 4-bit or reduce context length, batch size, or KV cache demands.

6

If quality drops too much, compare against a smaller native model in FP16 or BF16 instead of forcing a worse low-bit version.

7

For fine-tuning, test QLoRA or another parameter-efficient method instead of attempting full training of the entire model.

8

Freeze the winning combination of model, quantization, runtime, and prompt setup, then document it for reproducibility.

Good benchmark set

  • Real prompts from your task
  • Edge cases and long inputs
  • A few deterministic comparison prompts
  • Latency and memory measurements recorded side by side

What to record

  • Model name and exact quantized file
  • Runtime and version
  • GPU / CPU / RAM / VRAM hardware
  • Context length, batch size, and generation settings

Common Mistakes

  • Assuming parameter count alone tells you whether a model will fit; context and KV cache matter too.
  • Comparing different runtimes and blaming the quantization format instead of the kernel implementation.
  • Using the most aggressive 4-bit variant immediately without checking whether 5-bit or 6-bit gives a better quality-memory balance.
  • Ignoring activations, temporary buffers, or max context length when estimating memory needs.
  • Trying full fine-tuning when QLoRA or LoRA would solve the problem more cheaply.
  • Assuming BF16 is a memory optimization; it is not smaller than FP16.
  • Downloading random community quants without verifying provenance, compatibility, or evaluation results.
  • Forcing a heavily quantized large model when a smaller stronger model would be faster, cheaper, and more accurate.

When to Quantize vs Choose a Smaller Model

Quantize when

  • The larger model is clearly better on your task and just barely misses your hardware limits.
  • You need to keep a specific checkpoint, architecture, or tokenizer for compatibility reasons.
  • Your runtime has proven optimized support for the target format.
  • A 4-bit or 5-bit version still outperforms smaller alternatives on your evaluation set.

Choose a smaller model when

  • The quantized larger model becomes unstable, slow, or noticeably worse.
  • You want simpler deployment with fewer runtime quirks.
  • Your application values latency and reliability more than peak benchmark scores.
  • The smaller model in higher precision already meets quality requirements.
Best operational rule: compare end-to-end task success, not model prestige. A smaller model that runs cleanly at good speed often beats an awkward oversized model squeezed into 4-bit.

Final Decision Checklist

Before quantizing

  • Measure baseline VRAM and quality
  • Know your target context length
  • Choose a runtime compatible with your hardware
  • Define acceptable quality loss ahead of time
  • Prepare a representative prompt benchmark set

Before shipping

  • Benchmark multiple quantization levels, not just one
  • Confirm memory fits with margin, not just barely
  • Test long prompts and sustained generation
  • Document exact file, runtime, and settings
  • Compare against at least one smaller native model
