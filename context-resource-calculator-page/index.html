Core idea

Weights are the model itself. KV cache is memory the model builds while reading tokens. A model can fit in memory but still run out of room when you increase context length, batch size, or concurrent users.

Mental model

Why tokens consume memory

1. The model loads its weights

Before the model can answer anything, its learned parameters must be in memory. Think of weights as the model’s permanent knowledge machinery. Their size depends mostly on how many parameters the model has and how many bits each parameter uses after quantization.

Very roughly:

Weight memory ≈ parameter count × bytes per weight

A 7B model at 16-bit precision needs far more memory for weights than the same 7B model at 4-bit quantization.

2. Every processed token leaves a trail

As a decoder-only LLM reads your prompt, each layer stores keys and values so the model can attend back to earlier tokens. That stored history is the KV cache. The longer the context, the bigger the cache.

KV cache grows roughly linearly with token count

That is why doubling context from 8k to 16k can nearly double KV memory, even though the model weights stay the same.

A useful habit: always separate static memory (weights) from dynamic memory (KV cache, activations, runtime overhead, batch buffers, and output buffers).

The main variable cost

How to think about KV cache

What is stored?

For each token, each layer stores a key tensor and a value tensor. That gives the model a memory of earlier tokens when generating later ones.

Why two tensors?

Attention compares the current query against stored keys, then uses the corresponding values to assemble the context-aware representation. So the cache keeps both K and V.

Why linearly with tokens?

Every additional token creates another slice of cache at every layer. One token is cheap. Tens of thousands of tokens add up fast.

Rough decoder-only formula

For an estimate, a convenient formula is:

KV cache bytes ≈ tokens × layers × KV heads × head dimension × 2 × bytes per KV element × batch × concurrent sequences

  • tokens: prompt tokens kept in context, plus generated tokens if they remain in cache
  • layers: transformer block count
  • KV heads × head dimension: how wide each layer’s remembered state is
  • 2: one tensor for keys and one for values
  • bytes per KV element: often 2 bytes for fp16/bf16, but some runtimes use 1 byte or other schemes

Simplified intuition formula

When a model uses standard multi-head attention, KV heads × head dimension is often close to the model hidden size. With grouped-query attention, it is smaller by a ratio.

KV cache bytes ≈ tokens × layers × hidden size × 2 × bytes per KV element × GQA factor × batch × concurrency

Where GQA factor is roughly:

KV heads ÷ attention heads

If a model has 8 KV heads and 32 attention heads, the factor is 0.25. That can reduce KV memory a lot versus older full multi-head designs.

Compression

What changes with quantization level

Weights shrink directly

Moving from 16-bit to 4-bit can reduce weight memory to roughly one quarter, although real files and runtimes add metadata and alignment overhead.

KV cache may or may not shrink

Some runtimes still keep KV cache in fp16/bf16 even if weights are 4-bit. Others support int8 or more aggressive KV cache quantization. So weight quantization does not automatically mean cheap long context.

Quality and speed can move too

Lower-bit formats can trade some quality for memory savings and may change kernel efficiency. Different runtimes handle the tradeoff differently.

Format Typical weight bytes / parameter Main use Important caveat
16-bit 2.0 Higher fidelity, simpler support Heavy for consumer GPUs
8-bit 1.0 Moderate compression Still large for very long context
4-bit 0.5 Popular local inference compromise Real memory is often a bit above the ideal number
2–3 bit 0.25–0.375 Maximum compression experiments Compatibility and quality can become limiting factors
Implementation matters

What changes by architecture and runtime

1

Attention design

Models using grouped-query attention (GQA) or multi-query attention (MQA) store fewer KV heads than classic multi-head attention. That lowers KV memory per token.

2

Runtime memory planning

Frameworks differ in allocator behavior, page/block management, cache compaction, prefix caching, and how they reserve temporary buffers. The same model can fit in one runtime and fail in another.

3

Host RAM vs GPU VRAM

Some stacks offload layers or cache to system RAM. That can make a model runnable, but often at a big speed cost because RAM bandwidth is far below GPU VRAM bandwidth.

4

Sliding window, chunked attention, and prefix reuse

Certain architectures or serving systems avoid keeping every token equally “live.” These optimizations can reduce practical memory growth, but they do not erase the underlying need to account for token history.

Serving economics

Batch size and concurrent users

Batch size

If you process several sequences together, you often get better throughput, but memory usage rises because the runtime must hold more token states at once. In rough planning, batch size scales KV memory close to linearly.

Concurrent users

In a server, each active conversation may carry its own cache. Ten users with 8k-token conversations can be much more memory-hungry than one user at 8k, even if they share the same model weights.

Rule of thumb: weights are shared, but KV cache is usually per active sequence. That is why serving many users stresses memory differently from running one long chat locally.
Worked examples

Practical examples for different model sizes

Example A: 7B model, 4-bit, 8k context

  • Weights: about 3.5 GB idealized, often more like 4–5+ GB in practice with metadata and runtime overhead
  • KV cache: depends heavily on architecture; a modern GQA design might land in the low single-digit GB range at 8k
  • Takeaway: feasible on a 12–24 GB GPU, but concurrency can eat headroom fast

Example B: 13B model, 4-bit, 32k context

  • Weights: roughly 6.5 GB idealized before overhead
  • KV cache: long context now becomes a major budget item, often rivaling or exceeding weights depending on KV precision and GQA ratio
  • Takeaway: long context can turn a “fits comfortably” model into a tight memory problem

Example C: 70B model, 4-bit, 8k context

  • Weights: around 35 GB idealized before runtime overhead
  • KV cache: still meaningful, but weights dominate first
  • Takeaway: huge models are usually weight-limited on single GPUs even before context becomes the bottleneck

Example D: same model, more users

  • One 7B model’s weights may stay fixed around a few GB
  • But ten simultaneous 8k sessions can multiply the cache cost by around ten
  • Takeaway: serving systems often become cache-limited before they become weight-limited
Planning method

A beginner-friendly way to estimate resources

1

Estimate weight memory first

Parameters × bytes per parameter gives your first rough number. Then add real-world overhead because quantized formats are never perfectly ideal.

2

Estimate KV cache for your target context

Use layers, hidden size or head dimensions, GQA ratio, batch size, and concurrency. This tells you whether long context is viable.

3

Add runtime headroom

Do not plan to use 100% of VRAM. Memory fragmentation, temporary buffers, and system needs mean you usually want safety margin.

4

Test with realistic prompts

A benchmark using a tiny prompt can mislead you. Test prefills, long prompts, and concurrent traffic that resembles your actual use case.

Summary

The intuition to remember

Bigger model ≠ longer context

Model size mostly determines weight memory. Context length mostly determines KV cache. You need room for both.

Quantization helps, but not everywhere

4-bit weights are great for shrinking the model, but the KV cache may still remain at 16-bit unless your runtime supports KV quantization.

Serving multiplies cache

More users or larger batches can multiply dynamic memory even while the weight memory stays fixed.
